# 如何安全迁移有状态 Agent Runtime

> **问题场景**：需要把带有本地补丁、插件和自定义能力的 Agent Runtime 迁移到另一台机器，同时保留目标机自己的身份、记忆、会话、任务和凭据。如何避免把代码部署变成全目录覆盖，并在验收后只留下可运行成品？

有状态 [[agent-harness|Agent Harness]] 的迁移不是普通应用发布。它同时涉及可重建代码、持久状态、机器身份、秘密和常驻服务；任何一层边界不清，都可能导致补丁错位、身份串用、历史丢失或旧服务继续运行。[[hermes-agent|Hermes Agent]] 是这一问题的具体实现案例。^[[[_living/AI-Applications/Hermes-Agent-macOS-Ops|Hermes-Agent-macOS-Ops]]]

## Step 1：先定义状态所有权

把目标目录拆成五类：

1. **可复现代码**：Git checkout、补丁和 lockfile。
2. **功能资产**：自定义 skills、插件、必要脚本和独立运行时。
3. **目标持久状态**：SOUL、memory、sessions、cron 和业务数据库。
4. **目标本地配置与凭据**：身份、群聊、路径、服务定义和密钥。
5. **过程材料**：staging、压缩包、patch 说明、迁移报告、测试输出和临时备份。

前两类可以迁移，第三类默认原地保留，第四类必须重建或在目标机就地恢复，第五类只允许在迁移事务期间存在。

## Step 2：记录不变量和授权矩阵

开始写入前记录：

- 源码 HEAD、remote 和 worktree 状态；
- 目标持久状态的哈希、计数和路径；
- Python、Node、包管理器和系统服务的实际版本；
- 允许复制、只允许目标机复用、必须留空的凭据字段；
- 允许迁移和明确排除的 skills、插件、MCP、群聊与任务。

这一清单既是实施边界，也是最终验收依据。没有明确授权的秘密默认不迁移。

## Step 3：用相同 Git 基线重建代码

网络稳定时可以在目标机获取源码；网络慢时，在源机从当前 HEAD 建立干净 clone 并打包传输。两种方式都必须保证：

- 目标 `HEAD` 与源机基线一致；
- patch 在干净树上通过预检查；
- patch 应用后改动集合符合预期；
- 反向检查可以识别整套 patch；
- remote 最终指向真实上游，而不是源机文件路径。

不要把源机脏工作树直接当作部署产物。否则无法区分本地补丁、未跟踪文件、生成缓存和个人状态。

## Step 4：按 allowlist 迁移能力

只复制明确需要的功能资产。未部署能力要从多个层面一起移除：配置入口、toolset、插件 allowlist、信任列表、脚本和服务注册。

如果 [[model-context-protocol|MCP]] 服务不在目标范围内，仅删除 server 配置仍不够；还要确认平台工具集合不会暴露其工具，插件也没有残留授权入口。

过程文档、patch bundle 和迁移脚本不属于运行能力。它们可以在 staging 中辅助验证，但不应留在最终安装目录。

## Step 5：重建身份和配置

配置应从功能模板和目标机事实组合，而不是选择任一侧整体覆盖：

- 行为开关和功能结构来自已验证模板；
- 主人、群聊、机器路径和服务参数来自目标机；
- 凭据只按授权矩阵迁移；
- 未配置的集成保持 disabled，避免空认证头；
- reasoning/thinking 等用户可见行为要在全局和平台层同时检查。

飞书等平台的应用作用域 ID 不能跨应用复用。人员表应使用租户级稳定 ID 关联旧画像与新应用 ID；主人固定置顶，其他人员按组织定义的稳定键排序。

当新 API 快照把某一客观字段对所有人员都省略时，应先判断为字段级权限不足，并保留已有值。不能把权限收窄误解释为全员数据删除。

## Step 6：验证真实运行时

不要只比较版本字符串：

- Python 需要检查 venv 一致性、lockfile 解析、native extra 和真实 import。
- Node 与 npm 的 engines 分别验证。
- shell PATH 与 launchd PATH 分别验证。
- 浏览器缓存、桌面二进制和独立工具 venv 分别判断，不能捆绑处理。

如果目标机无法可靠重建完整依赖，而两端架构和系统 ABI 兼容，可以迁移经过验证的运行时；随后必须重写绝对路径，并重新执行依赖检查和测试。

## Step 7：在 staging 中完成闭环验证

切换前至少验证：

- Git 基线、patch 和工作树；
- 配置解析及敏感信息扫描；
- 核心 import 和补丁相关测试；
- 自定义插件、沙箱、文档、图片与图表能力；
- 主模型、各 fallback 和辅助模型的真实最小请求；
- 人员身份、主人绑定、群 allowlist 和权限拒绝路径。

测试应使用隔离 home，避免把测试生成的记忆、会话、cron 或数据库带入生产目录。

## Step 8：执行可回滚切换

1. 停止旧 gateway，等待活动任务排空。
2. 保存最后一刻的目标持久状态快照。
3. 将旧源码整体移出活动路径。
4. 将已验证的新源码移入固定路径。
5. 重定位 runtime 中的绝对路径。
6. 只安装 allowlist 中的外围资产。
7. 写入最终配置和目标机凭据。
8. 重建系统服务并验证 supervisor 与子进程。
9. 复跑关键测试、模型请求和状态不变量检查。

在这一步完成前，备份是回滚能力，不能提前删除。

## Step 9：验收后清理过程材料

获得用户确认后，删除：

- staging、测试 home 和 model probe；
- 传输归档、校验文件和临时 patch；
- apply 演练仓库、失败 venv 和旧源码副本；
- 迁移脚本、部署报告、patch 说明和升级 playbook；
- 含旧密钥的环境或 credential 备份；
- 退役服务的脚本、plist、launchd 注册和残留进程；
- 测试缓存和无用平台缓存。

不要根据文件名宽泛删除。官方仓库自带的 README、docs、测试和迁移模块，以及 skill 运行时说明，属于完整安装的一部分；目标持久状态更不能因“清理”被删除。

## 最终判定

迁移只有在以下条件同时成立时才算完成：

- 代码基线与补丁集合可证明；
- 目标持久状态保持不变；
- 身份、群聊和权限边界属于目标机；
- 凭据来源符合逐字段授权；
- 运行时与系统服务真实可用；
- 功能回归和模型请求通过；
- 迁移中间态、备份和过程文档已按授权清理。

这套方法把部署从“复制目录”改造成一个有准备、验证、切换、回滚和清理边界的事务。它适用于任何同时拥有本地补丁、长期状态和机器级凭据的 Agent Runtime。
