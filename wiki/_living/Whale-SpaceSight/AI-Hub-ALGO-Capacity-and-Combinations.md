# AI Hub 上的 ALGO 版本、路数与组合边界

本文是 SpaceSight AI Hub 上 Edge ALGO 包型、实测路数、能力组合和接入拓扑的**唯一维护入口**。其他 living 文档只描述硬件原理、算法职责或业务背景，不重复维护本文的版本与容量数字。

> [!important] 先看负载口径
> **标准客流 ALGO、视线检测专用 ALGO、端侧检测 + ReID 和其他专项模型是不同负载。** 同一台盒子在不同负载下的路数不能横向替换。厂商标称的视频分析路数也不能直接当成 SpaceSight ALGO 的业务路数。

## 1. 统一口径

### 1.1 用 SoC 消除盒子名称歧义

现有测试记录对低档算能盒子同时使用了“7.2T”和“7.5T”两个名称；两处都指向 `CV186AH`。因此容量评估时应以 SoC 为主键：

| 历史记录中的盒子名称 | SoC       | 本文统一写法                |
| -------------------- | --------- | --------------------------- |
| 算能 7.2T / 7.5T     | `CV186AH` | CV186AH 盒子（7.2T / 7.5T） |
| 算能 16T             | `BM1688`  | BM1688 盒子（16T）          |
| 算能 32T             | `BM1684X` | BM1684X 盒子（32T）         |
| RK3576 盒子          | `RK3576`  | RK3576 盒子                 |

`CV186AH`、`BM1688`、`BM1684X` 和 `RK3576` 是计算平台，不是完整整机 SKU。相同 SoC 的不同主板、内存、固件、散热和 Runtime 仍需分别验收。

### 1.2“路数”不等于“算法数量”

- **一路**表示一路并发视频通道。选路数前必须先选 ALGO 序列：出入口版本、标准店内版本或视线店内版本。出入口版本支持脚部划线和头肩划线；标准店内版本默认带试乘试驾/试乘试坐能力，但可按通道关闭；视线检测使用单独的店内版本序列。
- **端侧能力数量**不能直接相加成视频路数。视线、端侧 ReID 等叠加能力会增加模型、预处理或后处理负载，但其等价路数必须由压测给出，不能按名称个数推算。
- **排队和看车不属于 Edge ALGO**，而是云端 Airflow 的业务处理逻辑。它们可以与端侧能力组成同一业务方案，但不产生端侧 ALGO 包型，也不折算盒子视频路数。
- **端到端功能 PASS**不等于所有指标都在盒子上计算。压测报告同时验证了边缘事件、截图上传和 T+1 展示；热力图、动线、顾客旅程等下游结果不能据此全部归为端侧模型。
- **“适合跑”不是硬件理论上限**。它是测试报告给出的工程建议上限；正式交付仍需在目标版本和现场码流下复测。

### 1.3 记录状态

| 状态         | 含义                                              | 能否直接作为交付路数                                 |
| ------------ | ------------------------------------------------- | ---------------------------------------------------- |
| 报告判定适合 | 测试报告列出该组合，并完成对应环境的功能/长稳测试 | 只能在相同版本和测试边界下作为方案依据，现场仍需验收 |
| 报告判定通过 | 测试报告将容量组合与长稳测试结论标为“通过”        | 只能在相同构建、模型组合和测试边界下作为方案依据     |
| 测试上限     | 测试记录给出明确负载上限，但未附完整独立长稳明细  | 可用于初始方案，必须补现场峰值与长稳验收             |
| 研发估算     | 方案仍在开发或数字来自估算规则                    | 不能作为交付承诺                                     |
| 未测试       | 当前维护记录没有该组合的容量与长稳结论            | 不能给出固定路数                                     |

## 2. 端侧包与云端逻辑登记

本节先登记 Edge ALGO 包型，再登记容易与 ALGO 混淆的云端业务逻辑，不重复容量数字。第 3 节通过 `PKG-*` 编号引用端侧版本口径。

### 2.1 Edge ALGO 版本树

| 序列编号                 | 版本大类     | 内置 / 支持能力                             | 开关与继承关系                                                         |
| ------------------------ | ------------ | ------------------------------------------- | ---------------------------------------------------------------------- |
| `PKG-ENTRANCE`           | 出入口版本   | 支持脚部划线和头肩划线                      | 两种划线方式属于同一出入口版本的配置能力，不据此拆成两个版本或两份路数 |
| `PKG-INTERIOR`           | 标准店内版本 | 默认带试乘试驾/试乘试坐；两种称呼指同一能力 | 能力随店内版本提供，可选择不开启；关闭能力不等于切换到另一条版本序列   |
| `PKG-INTERIOR-ATTENTION` | 视线店内版本 | 包含店内能力并叠加视线检测                  | 使用单独的版本序列，不是在 `PKG-INTERIOR` 上临时打开普通功能开关       |

### 2.3 云端 Airflow 业务逻辑

| 逻辑编号             | 业务逻辑 | 运行位置     | 与 Edge ALGO 的关系                                                           |
| -------------------- | -------- | ------------ | ----------------------------------------------------------------------------- |
| `FLOW-QUEUE-AIRFLOW` | 排队     | 云端 Airflow | 消费端侧上报的基础轨迹/区域数据；不是 ALGO 功能，不形成 ALGO 包或盒子容量记录 |
| `FLOW-LOOK-AIRFLOW`  | 看车     | 云端 Airflow | 消费端侧上报的店内轨迹/区域数据；不是 ALGO 功能，不形成 ALGO 包或盒子容量记录 |

排队配置中列出标准 ALGO 包，是因为云端处理仍依赖店内 ALGO 提供上游数据；若同一项目还要求视线，则需要部署视线版本以提供视线能力。这个依赖关系不表示排队运行在 ALGO 内。

### 3.1 主台账的适用规则

- 标准出入口与店内容量记录只适用于 2025-08-26 标准客流测试边界，不能直接迁移到后续发布版本、`PKG-INTERIOR-ATTENTION` 或端侧 ReID。
- 测试记录没有列出的混合比例仍是未知组合。即使总路数相同，也不能用线性插值补出新记录。
- **试乘试驾与试乘试坐是同一项店内 ALGO 能力**，不是两个模型或两个包型。测试记录没有说明该能力启用了几路，因此仍不能从组合名称推算等价路数。
- 测试场景名称中的“看车”属于 `FLOW-LOOK-AIRFLOW`，不是端侧专项模型，不能把它计入 ALGO 算力成本。
- 端侧检测 + ReID 是把 ReID 推理进一步下沉到盒子的研发负载，与标准链路把数据交给云端 TRAJEX 不同；对应估算不能用来替换标准客流记录，也不能外推为其他盒子的实测能力。
- RK3576 容量只适用于双 NPU 融合测试场景。测试报告没有精确 ALGO 版本号，也没有写明车门识别通道数量，不能将两条记录扩展成任意组合。

## 4. 标准客流压测边界

### 4.1 码流与长稳条件

`CAP-CV-STD-*` 和 `CAP-BM-STD-*` 使用的网络/录像子码流为 704 x 576、25 FPS、512 Kbps、GOP 50；事件/定时录像主码流为 1920 x 1080、25 FPS、2048 Kbps、GOP 50，并要求事件与定时编码参数保持一致。

当前测试记录中的编码字段显示为 `H25`，无法据此确认是 H.264 还是 H.265，交付时必须回到 NVR/IPC 页面核实真实编码。提高分辨率、码率或输入 FPS 后，原容量记录不再自动成立。

标准客流测试记录了 3 x 24 小时运行期间直播、录像、推理、事件触发、截图上传、VPP 内存和 TPU 占用等功能正常。这个长稳结果仍受包版本、码流、测试设备和运行模式约束；提高并发人数或增加专项模型后应重新压测。

### 4.2 端到端功能与端侧职责

报告回归了店内/出入口事件、截图、人脸马赛克、轨迹、区域客流、停留、热力图、动线、区域关注、顾客旅程、员工去重、ReID 数据和年龄性别等结果。这是端到端功能清单，不表示每个指标都由 AI Hub 上的一个独立模型直接计算。

容量评估应按真实端侧负载拆分：视频解码与预处理、人体/车辆检测、跟踪、事件与属性抽取、截图和上报属于 Edge ALGO 主链路；云端或 T+1 后处理生成的指标不应重复计入端侧模型数量。

## 5. ALGO 版本能力与云端业务边界

### 5.1 出入口版本

`PKG-ENTRANCE` 支持两种划线方式：**脚部划线**和**头肩划线**。它们是同一出入口版本内的配置能力，不是两个 ALGO 版本。当前测试记录没有分别给出两种划线方式的容量差异，因此第 3 节只按出入口路数维护；后续若压测证明二者负载不同，再新增独立容量记录。

### 5.2 标准店内版本与试乘能力

`PKG-INTERIOR` 默认带试乘试驾/试乘试坐能力，但可以选择不开启。试乘试驾与试乘试坐是同一个能力，不另设独立包序列。涉及该能力的盒子路数只查第 3 节明确标记“试乘开启”的记录；其余店内组合未记录开关状态，本文不假设默认开启或关闭。

### 5.3 视线检测店内版本

视线项目应选择独立的 `PKG-INTERIOR-ATTENTION` 版本序列，容量只查 `CAP-CV-ATT-01` 或 `CAP-BM-ATT-01`。它不是标准店内版本上的普通功能开关。如果只有部分店内通道使用视线版本，当前测试记录没有给出可增加到多少总路数，不能线性插值。

视线能力只能配置在店内客流相机上，并需要配置两种区域：

- **客流检测区域**：按人体框底部中点，也就是人的脚部位置做区域过滤；范围只需覆盖关注区域附近，避免过大带来无效检测。
- **关注区域**：表示需要判断顾客是否关注的目标范围；一个客流检测区域可以绑定多个关注区域。
- 客流检测区域内的成年人站立像素高度应大于 250 px；过远区域不应纳入。
- 靠近摄像头的检测区域需要贴到画面底部，避免底部空隙把近处人员过滤掉。
- 视线功能应逐路配置；视线配置规则提示批量配置存在问题。若盒子端相机管理配置被删除，需要重新从平台下发每路功能配置。

主台账中的视线人群密度描述只适用于视线模型，不是整店总人数或标准客流的人数上限。

### 5.4 排队与看车

排队和看车都在云端 Airflow 中处理，不是 Edge ALGO 功能。方案只有排队或看车需求时，不应创建所谓 queue/look ALGO 包，也不应因为这两项云端逻辑减少盒子容量；盒子仍按实际启用的店内、出入口、视线、端侧 ReID 等端侧负载选型。

排队区域按人体框底部中点定义，区域应避开店员常驻位置；靠近摄像头时要贴到画面底部，避免近处人员被过滤。这是云端业务计算所需的空间配置，不表示过滤逻辑运行在盒子端。看车同样消费店内 ALGO 上报的基础轨迹与区域数据，再由 Airflow 计算业务结果。

| --------------------- | ---------------------------------------------------------------------- | ---------------------------------------- |
| `TOP-CV-ONE-NVR`      | CV186AH 盒子 + 16 路 NVR + 16 台 IPC                                   | PASS；一台盒子拉取一台 NVR 下的通道      |
| `TOP-BM-ONE-NVR`      | BM1688 盒子 + 32 路 NVR + 20 台 IPC                                    | PASS；一台盒子拉取一台 NVR 下的通道      |
| `TOP-TWO-BOX-ONE-NVR` | CV186AH + BM1688 两台盒子 + 同一台 16 路 NVR + 16 台 IPC               | PASS；两台盒子拉取同一 NVR 的不同通道    |
| `TOP-ONE-BOX-TWO-NVR` | CV186AH / BM1688 盒子拉取 16 路与 32 路两台 NVR 的通道，合计 32 台 IPC | 仅测试场景实现；测试记录注明线上尚未实现 |

所以“两台盒子共享同一台 NVR、各拉不同通道”在测试场景中通过；“一台盒子跨两台 NVR 拉流”不能因为测试 PASS 就直接作为线上标准方案。无论哪种拓扑，都要同时检查 NVR 的并发取流能力、子码流参数、鉴权、网络带宽和通道映射。

## 7. 满载监控与运行风险

### 7.1 RK3576 的 72 小时监控结果

以下数据与 `CAP-RK3576-01` 使用同一构建和 9 路满配场景：

| 观测项         | 测试记录                                                            |
| -------------- | ------------------------------------------------------------------- |
| 双 NPU 负载    | Core0 稳定 79%-88%，Core1 稳定 76%-85%；报告未见算力溢出结论        |
| 视频解码 FPS   | 所有通道 MPP 解码稳定 24.98-25.01 FPS，无丢帧                       |
| CPU / 进程资源 | ALGO 稳态 CPU 约 300% / 800%，整机资源充足；72 小时未见持续资源泄漏 |
| 服务稳定性     | supervisor 托管期间无闪退、线程死锁或断流，客流计数未出现跳变错乱   |

这些监控值证明的是指定融合构建在测试场景下的稳定性，不是所有 RK3576 ALGO 版本的固定运行参数。

### 7.2 已知风险

- **最大通道路数 + 离线缓存不支持**：标准客流测试明确指出，CV186AH / BM1688 在对应标准客流容量记录的最高负载下进入离线缓存会占用 VPP 内存，可能出现 `reopen` 错误、ALGO 异常和客流漏记。主台账中的标准容量应视为正常联网模式的建议上限，不能同时承诺满路数与持续离线缓存。
- **断网 PASS 不覆盖上述边界**：同一测试也记录了断电、断网恢复后数据正常上报，但没有证明该测试在最高负载和持续缓存压力下执行。更具体的满载缓存风险说明优先作为交付限制。
- **FPS 偶发下降**：测试记录显示 ALGO 极小概率出现取流 FPS 达不到测试输入值的情况。验收不能只看进程存活，还要连续检查每路输入/推理 FPS 和事件漏记。
- **温度边界**：测试记录只覆盖 65°C 运行正常，大于 70°C 未验证，不能向更高温度外推。
- **32T 单机审计不等于容量**：既有实机文档记录过 BM1684X 盒子的 NPU ION heap 满分配与 `ENOMEM`。这是特定时点的运行状态，只能提示模型加载和内存预算风险，不能反向推导稳定路数。
- **RK3576 断网 / 离线缓存风险**：RK3576 测试记录显示，完全断网环境下可能出现局域网 NVR 视频数据获取异常，约 20% 概率 RTSP 打开失败，约 50% 概率导致单一通道 FPS 下降。
- **RK3576 断网后拉起缺陷**：设备断网时，`supervisorctl` 重启后存在 ALGO 未运行、日志卡在同一位置的问题；缺陷表将其列为新发现且等待解决。
- **RK3576 车门框重叠风险**：车门检测框大面积重叠会降低试乘识别准确率，带来误检/漏检；部署时应避免重叠，后续模型需优化双分支特征隔离。
- **RK3576 运维告警**：报告建议增加 NPU 负载大于 90% 和单路 FPS 持续下降告警。它们是告警阈值建议，不是容量通过标准。

## 8. 组合选型与验收

### 8.1 逐路建立功能清单

为每台相机逐路列出以下信息，再匹配第 3 节主台账：

| 字段           | 示例                                                       |
| -------------- | ---------------------------------------------------------- |
| ALGO 序列      | `PKG-ENTRANCE` / `PKG-INTERIOR` / `PKG-INTERIOR-ATTENTION` |
| 出入口划线方式 | 脚部划线 / 头肩划线                                        |
| 基础能力       | 检测、跟踪、事件、截图、人脸打码、属性上报                 |
| 店内 ALGO 能力 | 试乘试驾/试乘试坐（同一能力）                              |
| 端侧叠加能力   | 视线、端侧 ReID、车门检测等专项模型                        |
| 云端业务逻辑   | 排队、看车；只记录数据与区域依赖，不计入盒子路数           |
| 端侧重模型     | 是否在盒子上运行 ReID 或其他特征模型                       |
| 峰值密度       | 画面内最大同时人数，视线通道尤其要单独记录                 |
| 输入流         | 编码、分辨率、FPS、码率、GOP、取流来源                     |
| 运行模式       | 正常联网 / 弱网 / 持续离线缓存                             |

然后按以下顺序决策：

1. 先把每路相机归到出入口、标准店内或视线店内序列；出入口再记录脚部/头肩划线，标准店内再记录试乘能力是否开启。
2. 试乘试驾/试乘试坐按同一个 `PKG-INTERIOR` 能力处理，只使用主台账明确标记“试乘开启”的对应记录。
3. 有视线检测时选择 `PKG-INTERIOR-ATTENTION`，只使用对应的 `CAP-*-ATT-*` 记录。
4. 有端侧 ReID、车门专项模型或其他新增模型时切换负载口径，不能继续引用标准客流记录。
5. 排队和看车只登记为 `FLOW-QUEUE-AIRFLOW`、`FLOW-LOOK-AIRFLOW` 的云端依赖，不改变 Edge ALGO 序列或盒子路数。
6. 拓扑涉及 `TOP-ONE-BOX-TWO-NVR`、满载离线缓存或测试记录未列出的端侧混合比例时，按非标方案做专项压测。

### 8.2 验收至少覆盖什么

- 固化整机 SKU、SoC、内存、OS/BSP、Runtime、ALGO 包编号、精确版本/构建和模型校验值。
- 使用现场真实 NVR/IPC 与目标码流，覆盖营业峰值的人数、遮挡、区域重叠和事件触发频率。
- 同时观察 CPU、NPU/TPU、VPP/ION、普通内存、每路输入 FPS、每路推理 FPS、温度、磁盘和缓存积压。
- 验证事件计数、截图上传和数据补传，不以“进程未退出”代替业务正确性。
- 分别测试正常联网、短时断网恢复和预计的离线缓存时长；满路数方案不得跳过离线压力测试。
- 按目标组合执行长稳测试，并记录丢帧、`reopen`、内存分配失败、服务重启和客流漏记。

## 9. 维护与更新

### 9.1 更新规则

本页更新时只同步版本、容量、测试边界和维护日期，避免同一知识点散落。

拿到新的测试报告或版本信息后，按以下顺序更新：

1. 更新第 2 节的 `PKG-*` 版本序列和测试报告时间；日期不明确时写“日期未注明”，不自行推测。
